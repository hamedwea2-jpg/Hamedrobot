# HeavenCloud Userbot

یوزربات تلگرام برای مدیریت **گروه‌های خودت**: ری‌اکشن خودکار + پاسخ خودکار پی‌وی.
ورود سشن کاملاً از طریق یک ربات تلگرام انجام می‌شود (نیازی به ترمینال نیست).

---

## فایل‌ها

| فایل | کار |
|---|---|
| `login_bot.py` | ربات ورود — شماره و کد را می‌گیرد و `data/session.txt` می‌سازد |
| `userbot.py` | یوزربات اصلی |
| `config.json` | همه تنظیمات |
| `deploy.sh` | نصب خودکار روی سرور |
| `*.service` | سرویس‌های systemd |
| `tests/` | تست رفتاری (بدون سشن واقعی) — ۷۴ + ۲۲ تست |

---

## راه‌اندازی سریع (لوکال)

```bash
pip install -r requirements.txt

# config.json را پر کن، بعد:
python login_bot.py        # در تلگرام /start و /login
python userbot.py          # بعد از ساخته شدن سشن
```

## Startup Command (پنل هاست)

اگر از پنل استفاده می‌کنی و فقط یک فیلد **Startup Command** داری:

```
python3 run.py
```

`run.py` هر دو را با هم بالا می‌آورد: ربات لاگین + یوزربات.
اگر سشن نباشد منتظر می‌ماند و به محض `/login` زدن، یوزربات را **خودکار**
استارت می‌کند — نیازی به ری‌استارت دستی نیست.

تنظیمات معمول پنل:

| فیلد | مقدار |
|---|---|
| Startup Command | `python3 run.py` |
| Python version | 3.10 یا بالاتر |
| Install command | `pip install -r requirements.txt` |
| Working directory | پوشه پروژه |

اگر پنل فقط فایل می‌خواهد نه دستور: `run.py`

**اجرای جداگانه** (اگر دو پروسه می‌توانی بسازی):
```
python3 login_bot.py     ← پروسه اول
python3 userbot.py       ← پروسه دوم، بعد از ساخت سشن
```

## منطق کار

**ری‌اکشن:** فقط در گروه‌های `allowed_chats`. هر پیام وارد یک صف تک‌نخی می‌شود؛
کارگر صف بین هر ری‌اکشن `random.uniform(min_delay, max_delay)` ثانیه صبر می‌کند.
ایموجی از لیست `available_reactions` همان گروه به‌صورت تصادفی انتخاب می‌شود
(اگر گروه محدودیت نداشته باشد، از کل ری‌اکشن‌های فعال تلگرام). هر کاربر در هر گروه
فقط یک بار در هر بازه cooldown ری‌اکشن می‌گیرد — در `data/state.db` ذخیره می‌شود.

**بالا رفتن خودکار `.delay` بعد از FloodWait:**

هر بار تلگرام محدود کند، ربات **خودش** هر دو عدد `.delay` را یکی ثانیه بالا
می‌برد و در کانفیگ ذخیره می‌کند — لازم نیست دستی عوضش کنی:

```
.delay 12 22   →  flood  →  .delay 13 23   →  flood  →  .delay 14 24  ...
```

تا رسیدن به `max_delay_cap` (پیش‌فرض `300`) ادامه دارد و بعد ثابت می‌ماند.
پیام FloodWait هم همین را می‌گوید:

```
⚠️ FloodWait — تلگرام محدود کرد

⏳ مدت: `637` ثانیه (`10m37s`)
📍 کجا: `ری‌اکشن [w1]`
⚙️ تنظیم قبل: `.delay 8 15` با `1` کارگر

🔼 خودکار زیاد شد: `.delay 8 15` ← `.delay 9 16`
✅ تنظیم الان: `.delay 9 16`
📊 در ۱ ساعت اخیر: `1` بار
```

**فاصلهٔ اجباری در هر گروه (`per_chat_gap`، پیش‌فرض `30`):**

تلگرام به درخواست‌های پشت‌سرهم در *یک گروه* حساس‌تر از همان تعداد پخش‌شده
بین چند گروه است. در لاگ واقعی‌ات ۴ ری‌اکشن پشت‌سرهم به یک گروه می‌رفت.
حالا بین دو ری‌اکشن در یک گروه حداقل ۳۰ ثانیه فاصله می‌افتد و ری‌اکشن‌ها
بین گروه‌ها پخش می‌شوند. `per_chat_gap: 0` خاموشش می‌کند.

**لاگ تمیز:**

تلگرام گاهی آپدیت خراب می‌فرستد و Telethon برای هرکدام یک خط
`Telegram is having internal issues` چاپ می‌کند. در لاگ تو **۱۳۳ خط از ۱۵۲
خط** همین بود. حالا فیلتر می‌شوند و لاگ فقط این را نشان می‌دهد:

```
[react] 😈  نام گروه  (-1004334103882)
[react] 🍾  گروه دیگر  (-1002854633530)
[flood] 637s at ری‌اکشن [w1] (delay 8-15s, 1 worker)
[auto-bump] delay 8-15 -> 9-16
```

**افزودن خودکار گروه (دیگر لازم نیست `.addchat` بزنی):**

روشن است (پیش‌فرض). هر گروه تازه‌ای که پیامی از آن برسد، **خودش** به لیست
فعال‌ها اضافه می‌شود و ربات همان لحظه شروع به کار می‌کند. برای هر گروهی که
اضافه شود یک پیام بهت می‌آید:

```
➕ گروه خودکار اضافه شد

👥 `نام گروه`
🆔 `-1001234567890`
👤 `1240` عضو
📊 امروز `3` گروه اضافه شده

حذف: `.delchat -1001234567890`
بلک دائمی: `.blockchat -1001234567890`
خاموش کردن: `.autochat off`
```

سه فیلتر برای اینکه گروه‌های بی‌ربط یا اسپم وارد نشوند:

| تنظیم | پیش‌فرض | معنا |
|---|---|---|
| `min_members` | `5` | گروه زیر این تعداد عضو اضافه نمی‌شود |
| `max_per_day` | `200` | سقف روزانه — جلوگیری از انفجار لیست |
| `exclude` | `[]` | بلک‌لیست — با `.blockchat` پر می‌شود |

`.chats` حالا نشان می‌دهد کدام گروه 🤖 خودکار اضافه شده و کدام ✋ دستی.

**پنجره حالا واقعاً اجرا می‌شود (نه فقط گزارش):**

تا پیش از این `window_hours` فقط در `.doctor` و `.window` *نمایش* داده می‌شد
و کارگر اصلاً نگاهش نمی‌کرد؛ یعنی همهٔ صف به‌ترتیب FIFO ری‌اکشن می‌گرفتند و
پنجره هیچ اثر اجرایی نداشت. حالا کارگر پیامِ بیرون از پنجره را رد می‌کند:

```python
if rc["window"] > 0 and time.time() - enqueued_at > rc["window"] * 3600:
    _queue_stats["stale"] += 1
    continue
```

عضو حذف نمی‌شود؛ با پیام تازه‌اش دوباره وارد می‌شود (تست سناریو ۲۱).

**گزارش FloodWait:**

هر بار تلگرام محدود کند، **خودِ ربات بهت پیام می‌دهد** — با مدت، جایی که
اتفاق افتاده، تنظیم فعلی، و پیشنهاد `.delay` جدید (۱.۵ برابر):

```
⚠️ FloodWait — تلگرام محدود کرد

⏳ مدت: `4321` ثانیه (`1h12m`)
📍 کجا: `ری‌اکشن [w1]`
⚙️ تنظیم فعلی: `.delay 20 30` با `1` کارگر
📊 در ۱ ساعت اخیر: `1` بار

👈 پیشنهاد: `.delay 30 45`

تاریخچهٔ کامل: `.flood`
```

حداکثر یک پیام در هر ۵ دقیقه (وگرنه خودِ پیام‌ها اسپم می‌شوند)، ولی همهٔ
موارد در تاریخچه ثبت می‌شوند. با `.flood` می‌بینی کدام تنظیم چقدر دوام آورد
— این‌طور حدِ امن اکانتت دستت می‌آید.

**ری‌اکشن ناموفق: صف تمیز می‌شود، عضو نمی‌سوزد**

`finally` کارگر همیشه اجرا می‌شود، پس آیتم پردازش‌شده دیگر در صف نمی‌ماند:

| خطا | از صف پاک می‌شود؟ | `reacted` ثبت می‌شود؟ | نتیجه برای عضو |
|---|---|---|---|
| `MessageIdInvalidError` (پیام حذف شده) | ✅ بله | ❌ نه | با پیام تازه‌اش برمی‌گردد |
| `ReactionInvalidError` (ایموجی/گروه بسته) | ✅ بله | ❌ نه | با پیام تازه‌اش برمی‌گردد |
| `RPCError` / خطای دیگر | ✅ بله | ❌ نه | با پیام تازه‌اش برمی‌گردد |
| `FloodWaitError` | ❌ **نه — می‌ماند** | ❌ نه | بعد از پایان محدودیت دوباره تلاش می‌شود |
| بیرون از پنجرهٔ ۱۲ ساعته | ✅ بله | ❌ نه | با پیام تازه‌اش برمی‌گردد |

نکتهٔ کلیدی: چون در حالت خطا `mark_reacted()` صدا زده **نمی‌شود**، عضو در
کول‌داون نمی‌رود. یعنی یک خطای موقت سهمیهٔ او را نمی‌سوزاند — فقط باید
پیام تازه‌ای بدهد تا دوباره وارد صف شود.

شمارندهٔ خطاها در `.doctor` دیده می‌شود: `❌ خطا: N`.

**گروهی که ری‌اکشنش بسته است نه اضافه می‌شود، نه می‌ماند:**

تلگرام دو جور ری‌اکشن را می‌بندد و ربات هر دو را چک می‌کند:

| حالت | فیلد تلگرام | پیام |
|---|---|---|
| مدیر کل ری‌اکشن را بسته | `available_reactions = ChatReactionsNone` | «ری‌اکشن در گروه بسته است» |
| ری‌اکشن برای اعضا ممنوع | `default_banned_rights.send_reactions` | «ری‌اکشن برای اعضا ممنوع است» |

سه جا اثر می‌گذارد:

۱. **افزودن خودکار:** گروه بسته اصلاً به لیست اضافه نمی‌شود.
۲. **کارگر:** قبل از هر ری‌اکشن چک می‌کند؛ اگر بسته بود درخواست نمی‌فرستد
   (هم سهمیه حفظ می‌شود هم `ReactionInvalidError` پشت‌سرهم نمی‌خورد).
۳. **چک دوره‌ای:** هر `reaction_check_hours` ساعت (پیش‌فرض `6`) همهٔ گروه‌ها
   دوباره چک می‌شوند. اگر گروهی ری‌اکشنش را بسته باشد، **از لیست بیرون
   می‌رود** و پیامش بهت می‌آید:

```
🚫 گروه از لیست بیرون رفت

👥 `نام گروه`
🆔 `-1001234567890`
📌 دلیل: ری‌اکشن در گروه بسته است

اگر دوباره باز شد: `.addchat` داخل همان گروه
```

`.chatcheck` همین کار را **همین حالا** و دستی انجام می‌دهد.

اگر چک ناموفق باشد (قطعی شبکه و…) گروه **حذف نمی‌شود** — حذف اشتباه یک
گروه فعال خیلی بدتر از یکی دو ری‌اکشن هدررفته است.

**سقف خودکار حالا واقعاً اجرا می‌شود**

تا پیش از این `active_limit()` فقط در `.doctor` و `.window` *نمایش* داده
می‌شد و هیچ‌جا جلوی ورود کسی را نمی‌گرفت — برای همین مجموعهٔ کاری از سقف
رد می‌شد (۳٬۵۴۴ نفر در برابر سقف ۳٬۴۵۶). حالا:

```python
if not await can_admit(chat_id, uid):
    return          # مجموعه پر است؛ عضو تازه فعلاً وارد نمی‌شود
```

قاعده‌ها:

| حالت | نتیجه |
|---|---|
| عضو تازه + مجموعه پر | ❌ رد می‌شود تا یک جا باز شود |
| عضو تازه + جا هست | ✅ وارد می‌شود |
| عضوی که از قبل جای دارد | ✅ همیشه؛ پیام تازه‌اش جایگزین قبلی می‌شود و مجموعه بزرگ‌تر نمی‌شود |
| یک نفر ری‌اکشن گرفت | یک جا آزاد می‌شود و نفر بعدی وارد می‌شود |

**ردشده‌ها حذف نمی‌شوند — هیچ‌کس برای همیشه از دست نمی‌رود**

وقتی مجموعه پر است، عضو تازه رد می‌شود. ولی **هیچ‌جا ثبت حذف نمی‌شود**؛
فقط آن پیامِ خاص وارد صف نمی‌شود. هر عضو در هر گروه فعال، هر وقت پیام
*تازه* بدهد و جایی باز باشد، وارد می‌شود:

```
عضو پیام می‌دهد ──> جا هست؟ ──بله──> وارد صف ──> ری‌اکشن
                        │
                        نه
                        │
                        └──> رد (موقت) ──> عضو هر وقت دوباره پیام بدهد، همین مسیر
```

**چرا پیام قدیمیِ عضو ردشده را دوباره وارد صف نمی‌کنیم؟** چون تا موقع خالی
شدن صف، آن پیام از پنجرهٔ ۱۲ ساعته بیرون رفته و کارگر ردش می‌کند. یعنی فقط
صف را شلوغ می‌کرد بدون هیچ فایده‌ای. راه درست، پیام تازهٔ خودِ عضو است.

چرخهٔ طبیعی هم خودش جا باز می‌کند: هر ری‌اکشن یک عضو را به کول‌داون
۳۰۰ ساعته می‌برد و جایش را آزاد می‌کند.

فرمول سقف:

```
سقف = ظرفیت روزانه × پنجره ÷ ۲۴
```

| تنظیم | ظرفیت روزانه | سقف در پنجرهٔ ۱۲h |
|---|---|---|
| ۱ کارگر × ۲۰–۳۰s | ۳٬۴۵۶ | ۱٬۷۲۸ |
| ۱ کارگر × ۹–۱۶s | ۶٬۹۱۲ | ۳٬۴۵۶ |
| ۱ کارگر × ۳–۶s | ۱۹٬۲۰۰ | ۹٬۶۰۰ |

`.doctor` حالا نشان می‌دهد مجموعه پر است یا نه:

```
👥 عضوهای در انتظار: `3` از سقف `3`  🔴 پر است
🎯 ردشده به‌خاطر پر بودن سقف: `1`
```

و وقتی سقف پر شود، **یک پیام در ساعت** بهت می‌آید (نه برای هر پیام).

**گروه تکراری اضافه نمی‌شود (race condition رفع شد)**

بین چک «این گروه قبلاً اضافه شده؟» و افزودن واقعی چند `await` هست (خواندن
ری‌اکشن‌های مجاز، خواندن تعداد اعضا). پس وقتی ۲۰ پیام هم‌زمان از یک گروه
تازه می‌رسید، **هر ۲۰ تا** از چک رد می‌شدند و هرکدام گروه را اضافه می‌کرد.
در لاگ واقعی یک گروه **۴۵ بار** اضافه شده بود.

حالا یک محافظ هم‌زمان (بدون `await`) قبل از اولین `await` علامت می‌زند:

```python
_adding_chats.add(chat_id)          # هم‌زمان، پس پیام موازی رد می‌شود
try:
    return await _do_auto_add(...)
finally:
    _adding_chats.discard(chat_id)  # حتی اگر خطا شود آزاد می‌شود
```

اثبات با تست: بدون محافظ **۲۰** درخواست شبکه، با محافظ **۱** تا.

ضمناً `dedupe_allowed_chats()` هنگام استارت تکراری‌های به‌جامانده از
نسخه‌های قبلی را پاک می‌کند (ترتیب حفظ می‌شود).

**`GetFullChatRequest` برای سوپرگروه کار نمی‌کند**

```
Invalid object ID for a chat ... megagroups are channels
```

سوپرگروه در تلگرام `channel` است، نه `chat`. حالا نوع entity تشخیص داده
می‌شود و درخواست درست صدا زده می‌شود — یعنی `min_members` برای سوپرگروه‌ها
هم واقعاً اعمال می‌شود (قبلاً همیشه `0 عضو` خوانده می‌شد).

**ترتیب ری‌اکشن: قدیمی‌ترین اول (FIFO)**

صف یک `asyncio.Queue` است، پس کارگر همیشه **قدیمی‌ترین** پیام را برمی‌دارد و
بعد جلو می‌رود. تست سناریو ۲۸ با پنج عضو با فاصلهٔ ۱۰ دقیقه‌ای این را ثابت
می‌کند:

```
ترتیب ری‌اکشن‌ها: [97001, 97002, 97003, 97004, 97005]
✅ قدیمی‌ترین اول ری‌اکشن گرفت   [first=97001]
✅ جدیدترین آخر ری‌اکشن گرفت     [last=97005]
✅ ترتیب کاملاً FIFO بود
```

`per_chat_gap` این ترتیب را به هم نمی‌ریزد؛ فقط کارگر را نگه می‌دارد تا
فاصلهٔ آن گروه پر شود، بعد سراغ همان آیتم می‌رود.

**ربات پیامِ خودت را ادیت نمی‌کند:**

قبلاً وقتی خودت دستور می‌زدی، ربات جواب را جای پیامِ خودت می‌نوشت و متن
دستور ناپدید می‌شد. حالا همیشه یک **پیام تازه** می‌فرستد:

- **در پی‌وی:** `respond` — پیام مستقل، بدون هدرِ «در جواب به…»
- **در گروه:** `reply` — تا معلوم باشد جواب کدام دستور است

در هر دو حالت پیام اصلیِ تو دست‌نخورده می‌ماند.

**`max_age` با `window` فرق دارد — اشتباه نگیر:**

| | `.maxage` | `.window` |
|---|---|---|
| واحد | دقیقه | ساعت |
| پیش‌فرض | `0` (خاموش) | `12` |
| چه کار می‌کند | پیام قدیمی را **برای همیشه** رد می‌کند | پیام قدیمی را از **حالت فعال** بیرون می‌برد |
| عضو برمی‌گردد؟ | نه | بله، با پیام تازه‌اش |

خط «قدیمی‌ترین در صف» در `.doctor` دربارهٔ **`max_age`** است، نه پنجره.
پیش‌فرضش `0` است و **بهتر است همان `0` بماند** — چون پنجرهٔ ۱۲ ساعته خودش
کارِ «بیرون بردن پیام‌های کهنه» را می‌کند، ولی بدون اینکه عضو را بسوزاند.

اگر `max_age` را هم ۷۲۰ (۱۲ ساعت) بگذاری، عملاً همان پنجره است با این تفاوت
که عضو **دیگر برنمی‌گردد**. پس لازم نیست.

**پنجرهٔ کاری و سقف خودکار (`.window`):**

سقف «چند نفر هم‌زمان در حال کار» **عدد ثابت نیست** — از روی `.delay` و
`.workers` حساب می‌شود:

```
سقف خودکار = ظرفیت روزانه × پنجره ÷ ۲۴
```

| تنظیم | پنجره ۱۲ ساعت |
|---|---|
| ۱ کارگر × ۲۰–۳۰s | ۱٬۷۲۸ عضو |
| ۱ کارگر × ۳–۶s | ۹٬۶۰۰ عضو |
| ۳ کارگر × ۲۰–۳۰s | ۵٬۱۸۴ عضو |

هر ری‌اکشن که زده شود آن عضو می‌رود در کول‌داون و جایش باز می‌شود؛ عضو
تازه‌ای که پیام داده وارد می‌شود. عضوهای بیرون پنجره **حذف نمی‌شوند** —
فقط از حالت فعال بیرون‌اند و با پیام تازه‌شان برمی‌گردند.

**پاکسازی خودکار گروه‌ها (`.ttl`):**

اگر گروه «زمان پاکسازی خودکار» داشته باشد، پیامی که تا آن موقع ری‌اکشن
نگیرد **خودِ تلگرام پاکش می‌کند** — پس آن عضو هرگز ری‌اکشن نمی‌گیرد، هرچقدر
هم صف را بزرگ کنیم. `.ttl` می‌گوید از عضوهای در انتظار چند نفر به موقع
می‌رسند:

```
⏳ پاکسازی خودکار گروه‌ها: 1d0h
👥 عضوهای در انتظار: 15856
✅ به موقع ری‌اکشن می‌گیرند: ~7200
❌ پیامشان پاک می‌شود: ~8656
```

راه‌حلش فقط **افزایش نرخ** است: `.workers` بیشتر و/یا `.delay` کمتر.
ربات پیامِ از عمر گذشته را اصلاً امتحان نمی‌کند (هدر دادن سهمیه است) و اگر
پیامی وسط کار حذف شده باشد، دیگر ۸ تا ۱۶ ثانیه بابتش صبر نمی‌کند.

**صف نامحدود — هیچ عضوی جا نمی‌ماند:**

`max_queue` و `max_age_minutes` به‌صورت پیش‌فرض **۰ (نامحدود)** هستند.
هیچ پیامی دور ریخته نمی‌شود و هر عضو در هر بازهٔ کول‌داون دقیقاً یک
ری‌اکشن می‌گیرد — حتی اگر صف ده‌ها هزار نفر باشد.

چطور بدون «هنگ» ممکن است؟

- **خواب فقط بعد از درخواست واقعی:** آیتم ردشده (کول‌داون / حذف / ادغام)
  **صفر ثانیه** هزینه دارد. قبلاً کارگر بعد از *هر* آیتم ۲۰–۳۰ ثانیه
  می‌خوابید؛ ۳۰٬۳۶۵ آیتم یعنی ~۷ روز خواب که بیشترش بیهوده بود.
- **ادغام هم‌کاربر:** از هر کاربر فقط *جدیدترین* پیام در انتظار می‌ماند.
  کاربری که ۱۰۰ پیام داده فقط یک ری‌اکشن می‌گیرد، پس ۹۹ آیتم باقی
  بدون مصرف زمان رد می‌شوند.
- **چند کارگر (`.workers N`):** ظرفیت ضرب می‌شود، هر کارگر فاصلهٔ خودش را
  رعایت می‌کند.
- **`janitor`:** هر ۵ دقیقه ردیف‌های قدیمی دیتابیس را پاک می‌کند.

**ظرفیت فیزیکی (این محدودیت واقعی است، نه باگ):**

```
ظرفیت روزانه = تعداد کارگر × ۸۶۴۰۰ ÷ میانگین فاصله
```

| فاصله | ۱ کارگر | ۳ کارگر | ۵ کارگر |
|---|---|---|---|
| ۲۰–۳۰s | ۳٬۴۵۶ | ۱۰٬۳۶۸ | ۱۷٬۲۸۰ |
| ۸–۱۵s | ۷٬۵۱۳ | ۲۲٬۵۳۹ | ۳۷٬۵۶۵ |
| ۳–۵s | ۲۱٬۶۰۰ | ۶۴٬۸۰۰ | ۱۰۸٬۰۰۰ |

`.doctor` و `.workers` ظرفیت و «زمان رسیدن به همهٔ صف» را نشان می‌دهند و
اگر صف از ظرفیت یک روز بزرگ‌تر باشد هشدار می‌دهند.

**پی‌وی:** فقط به کسی که **خودش اول پیام داده**، فقط **یک بار** (`once_per_user`)،
با تاخیر طبیعی ۱.۵ تا ۴ ثانیه. ربات‌ها مستثنی هستند.

> **دیباگ پی‌وی:**
> - `.pmtest` → یک پی‌وی **واقعی** به خودت می‌فرستد. اگر تلگرام اجازه ندهد
>   (`PeerFloodError` / `FloodWait`) دلیلش را همان‌جا می‌گوید.
> - `.pmlog` → آخرین ۲۵ تصمیم را با دلیل نشان می‌دهد:
>   `ساعت | آیدی | ✅ ارسال شد / رد | دلیل`
> - اونر و ادمین‌ها به‌صورت پیش‌فرض مستثنی‌اند؛ با `.pmadmins on` شاملشان کن.
>
> 🔧 **باگ رفع‌شده:** قبلاً `event.sender` برای کسی که اولین بار پی‌وی می‌داد
> `None` بود (چون در کش entity تلگرام نیست) و هندلر **بی‌صدا** برمی‌گشت —
> برای همین هیچ پی‌وی‌ای جواب نمی‌گرفت. حالا در این حالت یک بار
> `get_sender()` صدا زده می‌شود. همان اصلاح روی هندلر گروه هم اعمال شد.

**FloodWait:** اگر تلگرام محدودیت بدهد، کارگر صف به‌طور خودکار به اندازه لازم می‌خوابد.
